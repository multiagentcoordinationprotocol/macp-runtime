## Context

Spec `main` merged #99 today. This repo's `conformance-oracle` CI job (`.github/workflows/ci.yml:555`) checks the spec repo out at `main` with no `ref:` (`:564-566`), so the job is **red on every new run right now**, in two independent places: `check_dir` (`:606-607`) reports 12 `MISSING` and 3 `DRIFT` lines, and `enum_lists_match_the_canonical_schemas` (`:646`, `crates/macp-policy/src/registry.rs:1638`) fails at `:1659` because `voting.threshold` moved from `minimum: 0` to `exclusiveMinimum: 0`. ## Design questions answered

**1. What selects schema-version-3 semantics at evaluation time?** The **policy's own `schema_version`**, read from `policy.schema_version` inside `evaluate_decision_commitment_outcome`. Not `semantics_rev`, and not both.

RFC-MACP-0012 §8 item 3 is explicit — "If the stored policy uses `schema_version` N, the runtime MUST evaluate using schema-version-N semantics, even if a newer schema version exists" — so the discriminator has to be a property of the **stored descriptor**, which is what `Session.policy_definition` is. A checkpoint serializes it inline and `try_replay_from_checkpoint` restores it verbatim, so on that path the binding is durable and replay-exact.

**Do not extend that claim to replay in general — it is false today, and an earlier draft of this plan leaned on it as a premise.** §8 item 1 ("The resolved `PolicyDescriptor` MUST be persisted as part of the session snapshot") and item 2 ("During replay, the runtime MUST use the stored `PolicyDescriptor`, never re-resolving from the registry") hold on the checkpoint path only. The **full-replay** path re-resolves from the live registry — `src/replay.rs:317-322`, `policy_registry.and_then(|pr| pr.resolve(&start_payload.policy_version).ok())` — which item 2 forbids in terms; and `src/replay.rs:63-70` *deliberately* falls back to full replay whenever a checkpoint lacks `policy_definition`. This is **pre-existing** and is not created by this work, but it is a second-order Phase 3 risk (an unregistered policy resolves to `None`, `enforce_commitment_policy` returns `Ok(())` early at `crates/macp-modes/src/mode/util.rs:125-127`, and the commitment is never policy-evaluated on replay). It is recorded as **Open question 6** and flagged for a spec-repo issue, not folded into this answer. What this design question needs from §8 is item 3 alone: *which* semantics apply is a property of the descriptor's declared version, wherever the descriptor came from.

`semantics_rev` is the wrong axis in both directions, and the failure is not hypothetical. It is one value per session, stamped from the binary's `CURRENT_SEMANTICS_REV` at `SessionStart` (`crates/macp-core/src/session.rs:28`, `src/runtime.rs:559`, recovered at `src/replay.rs:333`). It answers "which release accepted this history", which is a statement about the *runtime*. `schema_version` answers "which semantics did the policy author select", which is a statement about the *descriptor*. Two sessions started by the same binary in the same millisecond, one binding a v1 policy and one binding a v3 policy, must evaluate differently — a per-session revision number cannot express that at all. Gating on `semantics_rev` would make every v1 policy bound *after* the bump evaluate fail-closed (violating §8 item 3 and breaking `decision_empty_tally_legacy`) while every v3 policy bound to a pre-bump session evaluated fail-open (violating §4.1). Both are conformance failures.

What "versions 1–2 retain the legacy rule so stored sessions replay identically" means concretely here: a session bound to a v1 or v2 policy takes the `require_vote_quorum`-gated arm forever, on the same binary that evaluates a v3 session fail-closed, at acceptance time and at replay alike. Replay needs no new machinery — it re-enters the same evaluator with the same stored descriptor. Empirically confirmed: with the whole change applied, all 19 pre-existing conformance fixtures, `tests/replay_round_trip.rs` and the loader's `assert_replay_equivalence` gate stay green, and `decision_empty_tally_legacy` / `decision_legacy_require_vote_quorum` — the two fixtures that exist to pin the legacy arm — pass before and after.

The one genuine exception is Phase 3's weighted-electorate rule, which is keyed off nothing — it applies at every schema version. **Three arguments carry that decision. A fourth, which an earlier draft used, is false and is struck below; do not reuse it.**

(i) **The spec says so, in terms.** `decision-rules.schema.json`'s `voting.weights.description` at `b59af6a` states it verbatim: "This electorate rule is normative for EVERY schema version, not only 3." RFC-MACP-0012 §4.1's prose carries the same rule in slightly shorter words — "This electorate rule is normative for **every** schema version." Attribute the "not only 3" clause to the **schema**, not to §4.1; it is not in the RFC text.

(ii) **§8 accepts the resulting stored-replay break in writing.** Its "Bounded exception — weight-`0` decisiveness (1.1.0-draft)" paragraph: "In exactly one configuration the original text *did* define an outcome that this rule reverses: a descriptor with an explicit `0` in `weights` (formerly schema-legal) plus `allow_decline_over_approval: true`, where a **Passed** tally whose only reject was cast by the weight-`0` participant formerly authorized a decline and no longer does. A stored session whose accepted history contains a decline accepted under that reading will not replay identically under this text. That break is accepted because it is vanishingly narrow, because descriptors with explicit `0` weights can no longer be admitted (Section 7), and because the reversed behavior was unsound: it granted a participant the policy author had explicitly stripped of voting weight the unilateral power to convert an approving weighted electorate's outcome into a decline." Read that paragraph for what it is: the **spec's** statement of which *normatively defined* outcome reverses. It is **not** a description of this runtime's blast radius — `unwrap_or(1.0)` makes the flip far wider here. See Phase 3's edge cases.

(iii) **Gating would add public API to a PR whose selling point is that it adds none.** `evaluate_decision_commitment_outcome` receives no `Session` — it gets the `PolicyDefinition`, the participants, the outcome direction and the mode state. Gating on `semantics_rev` therefore means threading it through the `macp_core::PolicyEvaluator` trait boundary. Survivable as a defaulted trait method, but it is new public surface on `macp-core`, and `release-plz.toml` runs `cargo-semver-checks` while computing the release PR (see Enterprise concerns).

**Struck, because it is false:** the argument that gating would fail `decision_weighted_zero_weight_v1.json` because it is a `schema_version: 1` fixture. It would not. `semantics_rev` is stamped at `SessionStart` from the **binary's** `CURRENT_SEMANTICS_REV` (`crates/macp-core/src/session.rs:135`), and `run_conformance_fixture` (`tests/conformance_loader.rs:388`) drives a real `rt.process(SessionStart)` at `:420-434` — so every fixture, v1 ones included, runs on a **freshly created** session at the current rev and would take the new behaviour under a gate. The fixtures cannot distinguish a gated from an ungated implementation at all.

**A correction to a premise this plan may have inherited: it is not true that every prior replay-affecting change in this repo was gated on `semantics_rev`.** `CURRENT_SEMANTICS_REV`'s own doc bullets (`crates/macp-core/src/session.rs:18-28`) list exactly two revisions, both Handoff implicit-accept clock changes. `docs/deployment.md` §4, "A negative weighted total now fails the Decision round" (`:61-63`), shipped **ungated**, and its stated justification is that "The case is reachable only from a directly-constructed `PolicyDefinition`, since registration already refuses negative weights." **That justification does not transfer to Phase 3.** An unlisted voter is reachable through an ordinary, schema-valid, *registered* policy — a `weighted` descriptor simply omits a declared participant from `weights`. Phase 3 is therefore not "another one like §4": it is the first ungated change in this repo that alters replay for a configuration an operator can author over the wire. State that contrast in the deployment note rather than implying continuity with §4.

**2. The evaluator's front-of-dispatch short-circuit.** `non_abstain_short_circuit_precedes_algorithm_dispatch` exists at `crates/macp-policy/src/evaluator.rs:1227` and guards the `non_abstain_total == 0 => NoVotes` return at `:337`. **It stays, and its assertion is unchanged**; the brief's instruction to retire it is based on issue #147's suggested fix, which #99 did not adopt. §4.1's empty-tally paragraph says the result "is **NoVotes** for *every* algorithm, never **Failed**", and that implementations "MUST report NoVotes so that two conformant runtimes agree on what they observed". **The strongest reason to keep the short-circuit is `unanimous`, not `plurality` — cite it first.** `check_voting_algorithm`'s `unanimous` arm is `participants.iter().all(…)` (`crates/macp-policy/src/evaluator.rs:379-396`), which is **vacuously true on an empty roster**; with `reject_count == 0` at `:386` the arm returns `Passed`, i.e. a *positive* pass on a session where nobody voted. §4.1 names this case in terms: "With **zero** declared participants the universally quantified predicate is vacuously true and MUST NOT be taken as a pass." The short-circuit at `:337` is the only thing standing between this runtime and that outcome, and Phase 5 is what makes an empty roster reachable at all — so the two are directly coupled (Phase 5 criterion 6 pins it). Secondarily, `plurality`'s own predicate would produce `Failed` on a 0-0 tie, so the short-circuit is also what makes this runtime conformant *there*. Either way it is what makes the runtime conformant, not what makes it non-conformant. What changes is downstream: the `VotingResult::NoVotes` arm at `:252`.

Its retirement is therefore a *re-basing*, and it is made visible three ways rather than silent: the test is **renamed** to `empty_decisive_tally_is_no_votes_for_every_algorithm` so the rename appears in the diff and cannot be mistaken for a deletion; its comment stops citing "blocked on spec issue #98" and cites RFC-MACP-0012 §4.1's MUST instead, changing it from a deferral guard into a conformance pin; and the behaviour it used to defer is replaced by two new named tests in the same module (`empty_tally_denies_a_positive_commitment_under_schema_version_3`, `empty_tally_under_schema_version_2_still_follows_require_vote_quorum`) placed adjacent to it. The same treatment applies to `zero_weighted_total_still_returns_no_votes` (`:1188`), whose assertion also survives but whose stated premise — that an all-zero `weights` map is schema-legal — dies with Phase 1; Phase 3 re-bases it onto an **unlisted** voter, which is the configuration that is still reachable.

**3. `{"a": 1.0, "b": -1.0}` — issue #148's open case.** #99 closes it at **registration**, which is where the reporter asked for it. `decision-rules.schema.json` now carries `voting.weights.additionalProperties.exclusiveMinimum: 0` plus `minProperties: 1`. `exclusiveMinimum: 0` excludes zero **and** every negative value a fortiori, so `{"a": 1.0, "b": -1.0}` is schema-invalid on `b` and `{}` is invalid outright. The canonical negative fixtures name only the two halves that were newly forbidden — `weights-explicit-zero.json` ("a legitimately zero-weighted observer is expressed by omission from this map, not by an explicit 0") and `weights-empty-map.json` — because negatives were already refused by this runtime's own mirror at `registry.rs:522`. After Phase 1 flips that filter from `< 0.0` to `<= 0.0`, the exact case in #148 is **unauthorable**: the descriptor cannot be registered, cannot be preloaded from `MACP_POLICIES_DIR`, and cannot reach the evaluator except by direct `PolicyDefinition` construction.

The evaluator half closes too, differently. `weighted_total == 0.0 => NoVotes` (`:419`) stays, but its reachable cause moves: previously it was an explicit-zero weight map, now it is a ballot set cast entirely by **unlisted** participants, which §4.1 defines as the empty decisive tally and §6.2 of RFC-MACP-0007 confirms is NoVotes at every schema version. So the arm goes from "undefined behaviour we deferred" to "the spec's named outcome for a named configuration". Net: #148's zero-sum case is closed twice over — unauthorable at admission, and defined at evaluation.

**4. Phase sequencing against the red CI.** **Implement first, vendor last** (Phase 6). Three reasons, in order of weight. (a) Vendoring is not inert: `every_fixture_is_registered` (`tests/conformance_loader.rs:616`) reads its own source with `include_str!` and fails if a vendored fixture has no `conformance_test!` line, so "vendor without registering" is not available — vendoring means running, and running 10 knowingly-failing tests is a knowingly-red tree. (b) The ordering does not change how long `conformance-oracle` is red on the PR anyway: `check_dir` compares this repo against spec `main` regardless of which of our commits is at HEAD, so that job is red from the branch's first push until Phase 6 lands, under either ordering. The only variable the ordering controls is whether *our own* suite is green at each commit, and implement-first keeps it green at all six. (c) Nothing reaches `main` red: `main` requires 12 status contexts with `strict: true`, so the branch merges as one green PR or not at all. Each of Phases 1–5 is independently verifiable **without** the fixtures, by unit tests it ships — which is also the anti-vacuity discipline, since the fixtures alone cannot distinguish a right denial from a wrong one.

**5. Are the 12 fixtures sufficient?** No, and the partition says why — see Context. Measured incrementally in the probe: widening `SUPPORTED_SCHEMA_VERSIONS` alone (Phase 2's one-line half) takes the passing count from **2 to 4**; adding the v3 empty-tally branch takes it to **8**; the weighted electorate rule to **10**; the objection-authorized decline to **11**; and the empty-participants relaxation to **12 of 12**, with the whole loader suite at 33/33. Phase 1 (registration mirrors) moves **zero** fixtures — it is gated entirely by the parity test, which is the other half of the red job.

## Long-term posture

The durable lesson of #99 is that `schema_version` is now a **semantic** axis and will be used again. The evaluator should treat "which schema version am I under" as a first-class, single-sourced question rather than an inline `>= 3` comparison repeated per rule as more semantic bumps land; the moment a second such comparison appears, extract it into a named predicate on `PolicyDefinition` with the version table in one doc comment, the way `CURRENT_SEMANTICS_REV`'s doc bullet list (`crates/macp-core/src/session.rs:18-27`) is the single place session revisions are described. One comparison does not justify the abstraction; three will.

The hand-written schema mirrors in `crates/macp-policy/src/registry.rs` cost this repo a red CI job on somebody else's merge, and will again. `enum_lists_match_the_canonical_schemas` is a good gate — it caught this within one spec commit — but it asserts equality of a hand-transcribed subset, so it catches *changes* to keywords someone thought to mirror and is blind to keywords nobody did. #99 added `minProperties` and a whole `allOf` arm; the parity test as written would have noticed neither. Phase 1 adds assertions for both, which is the right incremental move, but the structural answer is either a JSON-Schema evaluator behind a dev-dependency for the test only, or a generated mirror. Both are larger than this PR and neither is urgent.

`tests/conformance_loader.rs` has a hardcoded registration list and two guards that ignore `MACP_CONFORMANCE_FIXTURES_DIR` (`:618`, `:654`), so a fixture that exists only upstream is invisible to the Rust side and detectable only by the shell byte-compare. That is survivable because the byte-compare is load-bearing and runs first, but it means the Rust suite can never be the thing that tells you the corpus grew.

## Enterprise concerns

**Upgrade blast radius, in order.** Phase 1 can stop a runtime from starting: `MACP_POLICIES_DIR` preload aborts on the first rejection, and a deployment carrying a `voting.threshold: 0.0` or an explicit-zero `weights` entry that this release accepted will refuse to boot on the next. `MACP_POLICIES_DRY_RUN=1` is the pre-upgrade check and the deployment note must lead with it. Phase 3 is the only change that can alter a **stored** session's replay, and it is the item that needs the most care in the release notes. It is bounded to `weighted` policies with an out-of-electorate voter — **two conjuncts, not three; direction is not a filter.** An earlier draft restricted it to declines; that is §8's framing of which *spec-defined* outcome reverses, and it is wrong as a description of this runtime, where `evaluator.rs:508`'s `unwrap_or(1.0)` means the **positive** direction flips too and does so far more commonly (the worked example is in Phase 3's edge cases). Nor is the consequence a differing replay: an affected session **fails to replay**, and is either skipped with a `WARN` (the session vanishes from the registry on restart) or, under `MACP_STRICT_RECOVERY=1`, **blocks startup**. RFC-MACP-0012 §8 sanctions the change in writing; it does not bound the operational blast radius, and the deployment note must not let it appear to. Phases 2, 4 and 5 cannot affect any existing session: v3 policies could not previously be registered, the objection-authorized decline only moves a commitment from denied to allowed and a denial never entered accepted history (RFC-MACP-0001 §8.3), and Phase 5 is a pure relaxation.

**Governance semantics change under operators' feet only where they opted in.** A v1 or v2 policy behaves exactly as before, forever, which is the whole point of §8 — an operator who wants the fail-closed reading registers a new `schema_version: 3` descriptor rather than having one imposed. The one place that promise is qualified is Phase 3, and it should be stated as a qualification rather than buried.

**`MACP_POLICY_SCHEMAS_DIR` is documented in no tracked env table** (`README.md`, `docs/API.md`, `docs/deployment.md`), yet it is what the parity test reads and what a contributor needs to run the gate that will now be tripped by every upstream schema change. Issue #163 flagged this; Phase 1 should add it, with the warning that it must point at a **clean** spec checkout — a dirty sibling tree produces failures that do not exist in CI, which cost real time during this planning pass.

**Release shape.** `cargo semver-checks check-release --workspace` reports "no semver update required" for all seven crates on this change, measured. That is a genuine result and not the `D7` trap — but the trap still applies and must be re-checked at ship time the same way: the tool **exits 0 while printing "requires new major version"**, and with `[workspace.package].version` already at `0.7.5` it compares `0.7.5 -> 0.7.5` from cache. Read the printed `Summary` line for each of the seven crates; never branch on the exit status. Separately, this PR lands before G4, whose `DECISIONS.md` **D7** takes `0.8.0` for an unavoidable `constructible_struct_adds_field` break on `HandoffOfferRecord`. Nothing here forces a major bump, so this should ship under commit types that produce a patch or minor — if a `!` breaking marker were used, release-plz would cut `0.8.0` for *this* work and push G4 to `0.9.0` for no reason. This is also why Phase 5 **mode-scopes** rather than re-signing the core validator: adding a `mode` parameter to the existing `pub fn validate_canonical_session_start_payload` would be a `macp-core` signature break, and `release-plz.toml` sets `semver_check = true` with all seven crates in one `version_group`, so that break alone would cut `0.8.0` here. The chosen shape (move the rule inside the already-mode-aware `validate_strict_session_start_payload`, plus at most one **new** additive `pub fn`) changes no existing signature. That is a conventional-commit discipline question, not a code question, and it belongs in the PR description.

## Open questions

1. Does an objection-authorized decline also bypass `commitment.require_vote_quorum` and `evaluation.minimum_confidence`? RFC-MACP-0007 §6.2 exempts it from the tri-state and the decline guard and is silent on the other two. Phase 4 takes the conservative reading — both still apply — which no fixture can distinguish, because none combines `finalize_decline` with either gate. Worth a spec-repo issue rather than a local guess; if the answer is "bypasses everything", Phase 4's change is one conjunct wider.
2. Should `PolicyRegistry` refuse an unknown `schema_version` at registration rather than only at evaluation? Today `registry.rs:298` rejects `0` and nothing else, so a `schema_version: 7` descriptor registers cleanly and then denies every commitment in any session that binds it, with a message about an unsupported version arriving at commitment time rather than at authoring time. §3's "a runtime MUST accept every schema version it supports" arguably implies refusing the ones it does not. Out of scope here because it would change `RegisterPolicy` rejection behaviour for descriptors nobody can usefully author anyway, but it is the same fail-at-authoring-time argument that carried #149.
3. ~~Does Phase 5 make `Mode::authorize_sender`'s fail-open default newly reachable?~~ **Demoted — this is not an open question and does not gate this plan; file it as a standalone issue.** The premise that Phase 5 changes anything here is wrong. `ModeRegistry::requires_strict_session_start` (`crates/macp-modes/src/mode_registry.rs:450`) reads a **per-entry** `strict_session_start` flag, and dynamically registered extension modes get `false` (pinned by `mode_registry.rs:911`), so those modes **already accept an empty roster today** and the default `authorize_sender`'s `!session.participants.is_empty() && !contains(sender)` (`crates/macp-modes/src/mode/mod.rs:63`) is **already reachable** — same shape at `multi_round.rs:130` and `passthrough.rs:56`. Phase 5 neither creates nor widens that. Worth fixing on its own merits (an empty roster reading as "everyone is authorized" is a fail-open default), but it is independent work with its own risk surface and does not belong in this PR.
4. `decision_zero_participants.json`'s own comment notes that a positive `Commitment` in a zero-participant session is rejected by **mode** validation (no proposal, RFC-MACP-0007 §5 rule 5) before policy is consulted, and that its error code "is pinned by no RFC and by no registry" — which is why the fixture does not attempt one. This runtime does have a code for it; worth confirming which, and whether it is worth an upstream registry entry.
5. Does anything downstream pin `macp-policy`'s behaviour by version? Issues #147–#149 were filed by a consumer pinning `macp-policy =0.6.0` exactly, with documented downstream guards to be deleted "when this lands". Closing the three issues should say which release carries the fix so those guards can be removed, and should note that #148 is closed by a **registration refusal**, which is a different remedy from the evaluator change its reporter also offered.
6. **Full replay re-resolves the bound policy from the live registry, which RFC-MACP-0012 §8 item 2 forbids.** §8 item 2: "During replay, the runtime MUST use the stored `PolicyDescriptor`, never re-resolving from the registry." `src/replay.rs:317-322` does exactly that — `policy_registry.and_then(|pr| pr.resolve(&start_payload.policy_version).ok())` — and `src/replay.rs:63-70` *deliberately* falls back to full replay whenever a checkpoint lacks `policy_definition`, so the non-conformant path is the default for any session without a modern checkpoint. Consequences: a policy that has since been unregistered or edited resolves to something other than what the session bound, and when it resolves to `None`, `enforce_commitment_policy` returns `Ok(())` early (`crates/macp-modes/src/mode/util.rs:125-127`) and the commitment is **never policy-evaluated on replay at all**. `docs/deployment.md` items 2 (`:35`) and 3 (`:57`) already document the operational face of this without naming it as a spec violation. **This is pre-existing and is not created by this work** — it is moved here from Design question 1, where an earlier draft asserted the opposite ("already replay-exact") as a premise. It is a second-order Phase 3 risk, because Phase 3 is the change that makes policy re-evaluation on replay newly able to fail. Out of scope for this PR; worth a spec-repo issue and a follow-on plan.
