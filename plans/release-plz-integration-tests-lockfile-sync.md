# Plan — release-plz keeps `integration_tests/Cargo.lock` in sync

> Revision 2. A fresh-Opus reverification pass tested every claim in revision 1 against the
> real code and against live workflow-run logs. It found two blockers and six should-fixes;
> all are applied below, and the evidence is retained inline so `/implement` does not have to
> re-derive it.

## Context

`integration_tests/` is a **separate cargo workspace**, deliberately excluded from the root
one (`Cargo.toml:19` — `exclude = ["integration_tests"]`; it has its own target dir and runs
manually through the real gRPC boundary). Its manifest depends on the runtime by path only:

```toml
# integration_tests/Cargo.toml:8
macp-runtime = { path = ".." }
```

There is **no version requirement** on that dependency — but `integration_tests/Cargo.lock`
still *records* the resolved version of all seven `macp-*` crates. So when release-plz bumps
the shared workspace version, it regenerates the **root** `Cargo.lock` and never this one,
which is then stale until a human regenerates it.

This is recurring, not hypothetical. Paid by hand at least four times:

| Evidence | State found |
|---|---|
| `plans/rfc-macp-0013-commitment-hash-PROGRESS.md:61` | stale at `0.5.0` vs `0.6.1`; fixed as housekeeping commit `d3c0d66` |
| `plans/list-sessions-pagination-PROGRESS.md:60` | standing chore: "dependabot never updates it. Check staleness before pushing." |
| `plans/list-sessions-pagination.md:451` | ship-checklist step 7: check staleness before pushing |
| This session | stale at `0.7.1` vs released `0.7.3`; regenerated by hand in PR #150 |

PR #150 added a `cargo metadata --locked` guard to `ci.yml`'s Check job but **deliberately
scoped it to the root workspace**, with a comment (`ci.yml:77-83`, line numbers verified) that
says guarding `integration_tests` "would turn every release PR red" precisely because of this
staleness. That comment is the debt this plan pays off.

**Correction to the brief.** The goal statement says a stale lock "breaks the `integration` CI
job with misleading compile errors." That is recorded history, but **not true of the code
today**: the `integration` job (`ci.yml:476-522`) runs `cargo build` and `cargo test --test …`
with **no `--locked`** (verified at `ci.yml:504` and `ci.yml:510-515`), so cargo silently
repairs a stale lock at build time. `publish.yml` uses `--locked` but only against the root
workspace, which `integration_tests` never reaches. The genuine present-day cost is the
recurring manual chore plus the blocked guard — this plan is scoped to that.

**Live subject.** PR #144 ("chore: release v0.7.4", OPEN) carries exactly this staleness right
now: root `Cargo.toml:24` = `0.7.4`, its `integration_tests/Cargo.lock` `macp-runtime` =
`0.7.3`. It is the first real-world subject of Phase 1 and the reason Phase 2 must not land
first. **Do not close or modify #144** — Phase 1 self-heals it on the next push to `main`.

### What was ruled out, and why

1. **A release-plz hook.** Verified: release-plz has **no hooks at any phase** (open FR
   release-plz#2714; won't-implement release-plz#2352). `pre_release_hook` is a *cargo-release*
   feature, not a release-plz one. The only lockfile-adjacent knob is `[workspace]
   dependencies_update`, which governs the **root** lock only. **Not available.**
2. **A `pull_request`-triggered workflow.** Every release-plz PR stalls at GitHub's
   `action_required` gate — confirmed empirically across four runs on the PR-144 branch, all
   `completed/action_required`. Such a workflow would never fire unattended. **Structurally
   cannot work.**
3. **Folding `integration_tests` into the root workspace.** Contradicts the documented
   `exclude` rationale, pulls the crate into `cargo test --workspace`/MSRV/clippy, and shares a
   target dir the design separates. **Blast radius exceeds the problem.**
4. **Deleting the lockfile.** Forecloses goal (b) — with no lock, `--locked` is impossible —
   loses reproducibility, and orphans dependabot's `/integration_tests` entry. **Discards the
   thing we want to protect.**

**Chosen approach:** regenerate inside the `release-plz.yml` *run* (which triggers on
`push: main`, so it is never gated), in a **dedicated job**, pushing one commit onto the
release PR via release-plz's own documented "commit files to the release PR" pattern.

## Phases

### Phase 1 — Sync the lock on the release PR branch

- **Status:** DONE (`a7b6efc`, PR #155, 2 verify rounds). Divergence from plan: none in
  design, but the assertion required a correction the plan did not anticipate. Rev 2
  specified "no package present in both revisions may change version", implemented first
  as a `name -> version` dict — which cannot represent a crate present at two versions.
  This lock has **346 package blocks but only 310 distinct names**, so 36 entries were
  invisible: it failed *open* on a re-pin of a lower duplicate (`base64 0.22.1 -> 0.22.2`
  passed) and *closed* on a legitimate removal of a higher one. Now keyed `name ->
  {version: has_source}` and compared as per-name version **sets**. Also added beyond
  plan: a sanity floor (>=50 packages + the internal crates must be present, so a
  truncated lock cannot pass), malformed-block rejection, a positive `cargo metadata
  --locked` check proving the repair actually worked, a root-`Cargo.lock` dirtiness guard,
  `timeout-minutes`, and the push target taken from `pr.head_branch` rather than `git
  rev-parse --abbrev-ref HEAD` (which is only correct for same-repo PRs).
- **Delivers:** a `sync-integration-lock` job in `release-plz.yml` that regenerates
  `integration_tests/Cargo.lock` on the release PR whenever release-plz opens or refreshes it.
- **Depends on:** nothing. **Must land before or with Phase 2** (see Phase 2).
- **Files:** `.github/workflows/release-plz.yml`
- **Approach:**

  **(a) A separate job, not a step in `release-plz`.** This is the most important structural
  decision and it is a correctness fix, not tidiness. `publish` is gated on **both**
  `needs: release-plz` and `releases_created == 'true'` (`release-plz.yml:65-66`). The action
  runs `release-pr` *then* `release` in one invocation, so a single run can legitimately have
  `prs_created=true` **and** `releases_created=true`. If the sync lived inside the
  `release-plz` job, a network blip or a firing assertion would fail that job and **skip
  `publish`** — producing tags and a GitHub Release with no crates.io upload. That is verbatim
  the 0.6.1 incident the workflow header (`release-plz.yml:20-26`) exists to prevent. A
  separate job cannot gate `publish`.

  Requires promoting two new values through the existing `outputs:` block
  (`release-plz.yml:32-33`), which currently exposes only `releases_created`.

  **(b) Guard on `prs_created`, never on `pr != ''`.** At the pinned action SHA `2eb1d8b`,
  when no PR is produced the action emits the literal string `{}`, not an empty value:

  ```bash
  else
      prs_created=false
      first_pr="{}"        # NOT empty
  fi
  echo "pr=$first_pr" >> "$GITHUB_OUTPUT"
  ```

  So an `if: … .pr != ''` guard evaluates **true** on a run that produced no PR, and the job
  would fail trying to check out a null branch. Guard on the dedicated boolean.

  **(c) Commit as `github-actions[bot]` — load-bearing, not cosmetic.** release-plz branches on
  who authored the PR's extra commits (`release_plz_core/.../release_pr/mod.rs::handle_opened_pr`):
  if it finds any contributor whose login does **not** end in `[bot]`, it **closes the PR and
  opens a new one** ("closing pr … to preserve git history") with a new number and new branch.
  Only the all-bot path takes the `update_pr` force-push route that our idempotence argument
  assumes. Setting the identity explicitly is what keeps this from becoming permanent
  PR churn:

  ```bash
  git config user.name  "github-actions[bot]"
  git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
  ```

  This currently *happens* to work because the composite action runs its own `git-config`
  step first — an undocumented internal dependency that a future action bump could remove.
  Set it ourselves.

  **(d) Check out via `gh pr checkout <number>`**, per release-plz's own documented
  "commit files to the release PR" example, rather than fetching `head_branch`. It is simpler
  and immune to the branch rename that (c)'s close/reopen path would cause.
  `release-plz.yml:35-38` already satisfies its `persist-credentials` requirement.

  **(e) Regenerate with plain `cargo metadata`, never `cargo update`.** `cargo update` would
  refresh all registry dependencies to their newest permitted versions — silently bumping
  `tonic`, `tokio`, `rig-core` into a version-bump PR and fighting dependabot's
  `/integration_tests` entry. Cargo's lock repair is minimal. **Verified twice** by the
  reverification pass: simulating the exact release-plz bump produced **14 changed lines, all
  `version = "…"`, zero non-version lines**, and re-running against PR #144's real head
  (`d90439e`) gave `7 insertions / 7 deletions`. It works `--offline` and **does not touch the
  root `Cargo.lock`** (explicitly tested with the root lock left stale).

  **(f) Assert the right invariant.** The hazard is a silent **re-resolution of third-party
  pins**, not a change in package count. A legitimate repair can add or remove packages: commit
  `d3c0d66` regenerated this lock for `macp-core`'s new `sha2` dependency and was
  **`19 insertions, 57 deletions`** — nothing like version-lines-only. And
  `integration_tests/Cargo.lock:3` is `version = 4`, the **lockfile format version**, so a
  naive `version = ` prefix match would let a format bump through silently while the quoted
  form would hard-fail on it.

  So assert the precise rule: **no package present in both the old and new lock may change
  version, except the seven `macp-*` crates.** Additions and removals are permitted. Implement
  by parsing both lock revisions into name→version maps and diffing. On failure, print the
  offending entries and fail the job.

- **Edge cases & failure modes:**
  - *No release PR this run* → `prs_created == 'false'` → job skipped by its `if:`. (Guarding
    on `pr` instead would run and fail — see (b).)
  - *Lock already correct* → `git diff --quiet` → skip the commit; never push an empty one.
  - *release-plz force-pushes on a later run* → our commit is discarded and re-created next
    run. Idempotent **only on the bot-author path** — see (c).
  - *Case-(b) staleness reaches a release PR* (a `macp-*` crate changed deps without the second
    lock being regenerated): the sync repairs it, and the assertion in (f) permits it because
    no third-party pin changed. Phase 2 is what stops this reaching `main` in the first place.
  - *Concurrent runs*: `concurrency: release-plz-${{ github.ref }}` with
    `cancel-in-progress: false` (`release-plz.yml:11-13`) serializes runs.
  - *Push rejected* (branch moved mid-run): fail loudly. The next push to `main` re-runs it.
  - *Registry unavailable*: `cargo metadata` fails → the **sync job** fails, `publish` is
    unaffected by construction (a).
  - **A second `action_required` run appears on the PR, at a new head SHA.** `main` requires 12
    status contexts with `strict: true`, evaluated at the head SHA. A maintainer who approves
    only the earlier (release-plz) run leaves the new head with zero checks and the PR
    unmergeable. The job must **log the new head SHA prominently** so the right run is
    approved. This is new operator-facing friction and is documented in Phase 3.
- **Acceptance criteria:**
  1. `release-plz.yml` has a **separate job** (not a step in `release-plz`) for the sync;
     `publish` still declares only `needs: release-plz` and its unchanged `if:`.
  2. The `release-plz` job's `outputs:` block exposes `prs_created` and `pr` in addition to
     `releases_created`.
  3. The sync job's `if:` tests `prs_created == 'true'` — **not** `pr != ''`.
  4. The job sets `user.email` to a `…[bot]@users.noreply.github.com` address before committing.
  5. Regeneration uses `cargo metadata` (no `--locked`); the string `cargo update` does not
     appear.
  6. The assertion fails when a **non-`macp-*` package that exists in both revisions changes
     version**, and passes when packages are only added/removed or only `macp-*` versions change.
  7. No commit is made when the lock is unchanged.
  8. The job logs the resulting head SHA.
  9. `actionlint .github/workflows/release-plz.yml` is clean.
- **Tests:** No Rust test covers a workflow. Prove by **local simulation**, recorded in
  `PROGRESS.md` — restore the tree afterwards and verify `git status --porcelain` is clean:
  1. *Legitimate bump passes:* apply the exact edit release-plz makes (mirror
     `git show 6d5f32e -- Cargo.toml`), regenerate, confirm version-lines-only and that the
     assertion passes.
  2. *Assertion fires:* hand-edit a third-party pin (e.g. `tokio`) to a different version in the
     regenerated lock and confirm the assertion **rejects** it. A guard only ever seen passing
     is not a guard.
  3. *Case-(b) passes:* replay the shape of `d3c0d66` (a lock diff that adds/removes packages)
     and confirm the assertion permits it — this is the S4 regression.
  4. *Format-version bump:* confirm a change to `version = 4` (unquoted, line 3) is classified
     correctly rather than silently ignored.
- **Docs:** none — not user-visible until Phase 3.

### Phase 2 — Guard `integration_tests/Cargo.lock` in CI

- **Status:** DONE (branch `ci/guard-integration-tests-lockfile`, 2 verify rounds plus a
  pre-merge wording correction; merged as `c9650df`, PR #156). Divergence from plan: the
  plan scoped the guard narrowly, to a contributor editing `integration_tests/Cargo.toml`.
  The rule is in fact **wider** — this lock records the seven path crates' full dependency
  edges, so adding or removing a dependency in *any* workspace crate invalidates it.
  Proven, not assumed: appending `base64 = "0.22"` to `crates/macp-core/Cargo.toml` makes
  `cargo metadata --locked --manifest-path integration_tests/Cargo.toml` exit 101. The
  acceptance criteria and the shipped comment were widened to match.
- **Delivers:** CI fails any PR whose `integration_tests/Cargo.lock` disagrees with its
  manifest, closing the hole PR #150 had to leave open.
- **Depends on:** **Phase 1** — and the dependency is hard. Enabling this first reds every
  release PR, starting with the live #144.
- **Files:** `.github/workflows/ci.yml`
- **Approach:** Add `cargo metadata --locked --manifest-path integration_tests/Cargo.toml` to
  the **`integration` job** (`ci.yml:476-522`), *not* to the `check` job that holds the root
  guard.

  Siting it in `integration` is deliberate. `check` is **"Check (MSRV)"** and pins
  `RUSTUP_TOOLCHAIN: "1.89.0"` (`ci.yml:48`), but `integration_tests/Cargo.toml` declares no
  `rust-version` — so a future dependency raising its MSRV above 1.89 would red the MSRV job
  for a reason having nothing to do with lockfile consistency. The `integration` job runs the
  current toolchain, already caches `integration_tests` (`ci.yml:493-495`), and is the job that
  actually consumes this lock. It is also a required status context, so the guard is enforced.

  Then **rewrite the comment at `ci.yml:77-83`**, which currently states the opposite of what
  will be true ("Root workspace only, deliberately… guarding it here would turn every release
  PR red"). A comment contradicting the code is how the next person re-derives a wrong
  conclusion. It must say the guard now lives in `integration` and why Phase 1 makes that safe.

  Kept as its own phase because it is the piece that can red every release PR, and must be
  revertable without also reverting the sync.
- **Edge cases & failure modes:**
  - *Phase 1 has a latent bug* → a release PR goes red. Intended and loud; recoverable in one
    commit, unlike silent staleness.
  - *Contributor edits `integration_tests/Cargo.toml` without regenerating the lock* → their PR
    fails with a clear message instead of the mismatch reaching `main`. A new contributor-facing
    constraint, documented in Phase 3.
  - *dependabot PRs against `/integration_tests`* → it updates that lock, so the guard passes;
    and a #140-shaped manifest/lock mismatch there is now caught too.
  - **Rollback constraint:** reverting Phase 2 while keeping Phase 1 is **not** a supported
    rollback — Phase 2 is what keeps case-(b) staleness off `main`. Revert both, or neither.
- **Acceptance criteria:**
  1. The `integration` job runs `cargo metadata --locked --manifest-path integration_tests/Cargo.toml`
     before it builds.
  2. The `check` job's root-workspace guard is unchanged.
  3. The comment at `ci.yml:77-83` no longer claims the guard is root-only and points to where
     the second guard lives and why it is now safe.
  4. Both guards pass on this branch (verified locally).
  5. `actionlint .github/workflows/ci.yml` is clean; no other job is modified.
- **Tests:** Local verification recorded in `PROGRESS.md`: the new invocation passes on the
  current tree, and — by reverting `integration_tests/Cargo.lock` to its pre-#150 stale state —
  **fails**; then restore. Same fires-when-it-should discipline as Phase 1.
- **Docs:** none directly; Phase 3.

### Phase 3 — Document the invariant in a *tracked* file

- **Status:** DONE. Divergence from plan: acceptance criterion 1 was **widened** during
  implementation — review proved the constraint covers a dependency change in *any*
  workspace crate, not only `integration_tests/Cargo.toml` (see the scope note below).
- **Delivers:** the new contributor constraint and the release-time sync are documented where
  contributors can actually see them, and the standing manual chore is retired.
- **Depends on:** Phases 1 and 2.
- **Files:** `CONTRIBUTING.md`, `docs/testing.md`, `CLAUDE.md` *(local mirror only — see below)*
- **Approach:** **`CLAUDE.md` is gitignored in this working tree** (`.gitignore:20`;
  `git ls-files CLAUDE.md` returns nothing). Documenting only there would write the invariant
  into a file no contributor or reviewer ever sees — and there is currently **no tracked file
  describing the release process at all** (`grep -rl release-plz docs/ README.md` → no hits).

  So the tracked statement goes in **`CONTRIBUTING.md`**, which already has a `## Pull requests`
  section describing the CI gate (:59-62) and already mentions `integration_tests` (:22).
  Add the operator-facing note from Phase 1's last edge case — that a release PR will carry
  **two** `action_required` runs and the one at the **newer head SHA** is the one to approve.
  `docs/testing.md` (which has an `## Integration test suite` section at :17 and says nothing
  about lockfiles today) gets the same rule stated where the suite is documented, cross-linked
  to `CONTRIBUTING.md` rather than duplicated.

  **Scope correction — the rule is wider than this plan first stated.** Earlier revisions
  described the new constraint as "a contributor who edits `integration_tests/Cargo.toml` must
  commit the regenerated lock". That is an under-statement, proven empirically: adding
  `base64 = "0.22"` to `crates/macp-core/Cargo.toml` alone reds the Phase 2 guard (exit 101).
  `integration_tests/Cargo.lock` records the **full dependency edges of the seven path
  crates**, so adding, removing, or changing a dependency in **any** workspace crate —
  `crates/macp-*/Cargo.toml` **or** the root `Cargo.toml` — requires regenerating it in the
  same PR. The docs must state that wider rule, name the failing job
  (`Integration (tier 1 + 2, real gRPC boundary)`), and give the one-line fix:

  ```bash
  cargo metadata --manifest-path integration_tests/Cargo.toml --format-version 1 > /dev/null
  ```

  `CLAUDE.md` still gets the paragraph as the local mirror, but the phase report must state
  plainly that this edit is **not in the PR diff** because the file is ignored — not skipped.
  Do not force-add it; the ignore is deliberate.

  The chore lines in `plans/list-sessions-pagination*.md` are historical records of completed
  work and are **left untouched** — rewriting a finished plan's checklist would falsify the
  record.
- **Edge cases & failure modes:** none functional. The risk is under-documenting the *new*
  constraints (the CI failure and the two-runs approval trap), which is why this phase targets
  tracked files rather than only `CLAUDE.md`.
- **Acceptance criteria:**
  1. `CONTRIBUTING.md` states the **wide** rule — that a dependency change in *any* workspace
     crate (`crates/macp-*/Cargo.toml` or the root `Cargo.toml`, not only
     `integration_tests/Cargo.toml`) requires committing the regenerated
     `integration_tests/Cargo.lock` — names the CI job that fails otherwise
     (`Integration (tier 1 + 2, real gRPC boundary)`), and gives the regeneration command.
  2. `CONTRIBUTING.md` (or `docs/testing.md`) explains the two-`action_required`-runs situation
     on release PRs and which to approve.
  3. `docs/testing.md` carries the same wide lockfile rule in its integration-suite section,
     cross-referencing `CONTRIBUTING.md`.
  4. No claim in any doc contradicts the final `release-plz.yml` / `ci.yml`.
  5. The standing manual staleness chore is stated as retired in the live docs. The chore
     lines in `plans/list-sessions-pagination*.md` are **not** rewritten — they are historical
     records of completed work.
  6. The phase report states explicitly that the `CLAUDE.md` edit is absent from the PR diff
     because the file is gitignored.
- **Tests:** Prose — verified by reading each changed section against the final workflow files.
- **Docs:** this phase *is* the docs phase.

## Long-term posture

- **Nothing here is a one-way door.** Three workflow/doc changes, each revertable in one
  commit; no schema, no migration, no published-artifact impact. The one coupling to respect is
  Phase 1 ↔ Phase 2 (revert both or neither).
- **Debt deliberately not taken:** having CI *regenerate and commit* the lock on any PR that
  needs it. That turns a visible inconsistency into an invisible auto-fix and would have hidden
  the #140-class bug rather than surfacing it. **CI verifies; it does not mutate what it
  verifies.** The release-time sync is different in kind — it runs where the version bump is
  *authored*, not where it is checked.
- **Residual coupling:** two workspaces, two locks. Future lock-touching tooling must remember
  the second. Phase 3's docs are the mitigation.

## Enterprise concerns

- **Failure domain:** the sync is its own job. It cannot gate `publish` (Phase 1(a)) — that
  isolation is the whole reason for the job split, and it is what keeps a sync failure from
  reproducing the 0.6.1 tag-without-publish incident.
- **Rollback:** revert Phase 1 + Phase 2 together to return to the manual chore. Phase 3 is
  independent.
- **Observability:** the assertion prints the offending package pins when it fires; the job logs
  the new head SHA so the correct `action_required` run is approved.
- **Validation:** the first real release after this lands is the true end-to-end test, and
  **PR #144 is the first subject** — it currently carries the exact staleness, and Phase 1
  self-heals it on the next push to `main` (confirmed: the *update* path emits
  `prs_created=true` with the existing branch, run `34041003772`). Watch it; do not assume.
- **Security:** no new secrets or permissions. `contents: write` is already granted
  (`release-plz.yml:8`).
