## Proposed vectors

Each vector below was generated by direct canonical-proto encoding of the given `value`
(`0x0a` + varint length + UTF-8 value bytes) and independently verified this session against
`macp-runtime`'s actual shipped decode behavior (`crates/macp-modes/src/mode/multi_round.rs`'s
`parse_contribute_value`, Phase 1 test suite). **Deliberately no `legacy_json_hex` field**:
encoding these exact values as legacy JSON is precisely what collides with their own proto
encoding — the vector's whole point is that only the *proto* reading is safe for these values,
not that a safe legacy-JSON encoding exists for them too. `decode_only` is deliberately absent
(i.e. `false`): unlike `one_byte_varint_boundary` (the one existing vector without
`legacy_json_hex`), these vectors' protobuf encoding SHOULD be asserted round-trip-safe
(encode(value) == protobuf_hex), since that round-trip is exactly the mechanism the fix
depends on.

```json
{
  "name": "collision_leading_brace_13",
  "value": "{\"value\":\"x\"}",
  "protobuf_hex": "0a0d7b2276616c7565223a2278227d"
}
```

```json
{
  "name": "collision_leading_brace_32",
  "value": "{\"value\":\"aaaaaaaaaaaaaaaaaaaa\"}",
  "protobuf_hex": "0a207b2276616c7565223a226161616161616161616161616161616161616161227d"
}
```

```json
{
  "name": "collision_no_leading_brace_123",
  "value": "\"value\":\"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa\"}",
  "protobuf_hex": "0a7b2276616c7565223a2261616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161616161227d"
}
```

Why these three, and not others: at value byte-lengths 9, 10, 13, 32, the single-byte
protobuf length-varint (`0x09`, `0x0a`, `0x0d`, `0x20`) is itself insignificant JSON
whitespace, exposing the value's own bytes to a JSON parser; lengths 9 and 10 are physically
too short to hold a minimal `{"value":""}`-shaped object (12 bytes), so only 13 and 32 can
actually collide via that mechanism. At length 123, the length-varint byte is `0x7b` (the
literal `{`), which becomes the JSON object's own opening token rather than whitespace — a
structurally different mechanism, which is why `collision_no_leading_brace_123`'s `value`
has no leading `{` of its own (the externally-supplied one comes from the length byte).
Both mechanisms and all three exact lengths are independently re-derived and exhaustively
swept (lengths 1..=300, five value shapes) in `macp-runtime`'s Phase 1 test suite — see
`plans/parse-contribute-value-192.md`.

## `decode_order`/`source` addendum

Proposed one-sentence addition to `contribute_payload.source` (or a new adjacent field, at the
spec repo maintainers' discretion):

> "json" being tried first is, as of `macp-sdk-python` PR #77 and `macp-runtime` issue #192,
> qualified by a canonicality tie-break: a successful JSON parse is trusted only when the same
> bytes do NOT also round-trip byte-identically through the canonical protobuf encoding.
> `macp-sdk-typescript`'s status against this same collision class is unchecked (see "One
> consequence" below).

## One consequence this ask must disclose, not hide

`macp-runtime` only satisfies these vectors at `Session::semantics_rev >= 3` — a
`semantics_rev`-gated fix, not an unconditional one, because this runtime must keep replaying
already-persisted, already-collision-affected session histories to their original (wrong)
outcome forever (RFC-MACP-0003 §1). `macp-sdk-python`'s PR #77 applies its equivalent tie-break
unconditionally (no revision concept exists in that codebase). So:

- A **fresh** `macp-runtime` session (any session whose `SessionStart` is accepted after this
  ships) satisfies these vectors.
- A **legacy** `macp-runtime` session (`semantics_rev <= 2`, accepted before this ships) does
  **NOT** satisfy these vectors — it reproduces the pre-fix, wrong decode, by design.
- `macp-sdk-python` (client library, no replay-forever constraint) satisfies these vectors
  unconditionally.
- `macp-sdk-typescript`'s status is **unknown** — not checked by this ask (out of scope for a
  macp-runtime plan to audit a third sibling repo). Flagged here explicitly rather than assumed
  either way, so the spec-repo maintainers or that SDK's own maintainers can verify it
  independently.

If the spec repo accepts these vectors, its own text should reflect that this is a
per-implementation, and even per-session-vintage, guarantee — not an unconditional
cross-implementation one — or the manifest would silently assert something stronger than any
implementation actually provides for pre-existing data.

## Acceptance criteria (for whoever picks this up, in either repo)

1. The three vectors above (or a maintainer-revised version of them) are added to
   `schemas/parity/contract.json`'s `sections.contribute_payload.vectors`.
2. The `decode_order`/`source` addendum (or equivalent maintainer wording) is added.
3. `schemas/parity/README.md`'s "Open items" entry for this gap is updated or removed to
   reflect the new vectors' existence.
4. **Not done by this ask, and explicitly out of scope**: re-vendoring the updated manifest
   into `macp-runtime`. That is separate follow-up work in `macp-runtime`, gated on this
   spec-repo change actually landing, on its own timeline. When it happens, it needs:
   - `cp` the updated `schemas/parity/contract.json` into `tests/parity/contract.json`
     (byte-identical, per `tests/parity/SOURCE.md`'s vendoring process).
   - Bump `SPEC_REV` in `.github/workflows/ci.yml` to the new spec-repo commit.
   - Update the hardcoded `vectors.len() == 4` assertion in
     `tests/parity_contract.rs:456-461` to the new count (7, if all three land unchanged).
   - Update `tests/parity/SOURCE.md`'s pinned commit/date.
   - Confirm `contribute_payload_vectors_round_trip_through_the_real_codec` and
     `contribute_payload_first_byte_markers_match_vectors` pass unmodified against the new
     vectors (they should, since `macp-runtime`'s Phase 1 fix already produces exactly this
     round-trip behavior at `CURRENT_SEMANTICS_REV`).
