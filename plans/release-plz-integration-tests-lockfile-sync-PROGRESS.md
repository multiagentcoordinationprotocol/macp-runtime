### Phase 1 — sync the lock on the release PR branch

**Status: DONE.** Branch `ci/sync-integration-tests-lockfile`, commit **`d24d7dc`**, shipping

#### What shipped

A new `sync-integration-lock` **job** in `.github/workflows/release-plz.yml` — deliberately a
job and not a step, per finding S3. Gated on `prs_created == 'true'` (B1). It checks out the
release PR by number, regenerates `integration_tests/Cargo.lock` with `cargo metadata`,
asserts that only the internal crate pins moved, verifies the repair with
`cargo metadata --locked`, and commits + pushes as `github-actions[bot]` (B2), skipping
entirely when there is nothing to commit.

#### Round 1 verdict: GAPS

The verifier passed 7 of 9 acceptance criteria and all workflow-level checks (YAML parse,
`actionlint`, job/step wiring, `publish` untouched, `prs_created` guard, bot identity,
no-empty-commit path). It returned 9 gaps, all in or around the assertion step:

| ID | Gap | Closed by |
|----|-----|-----------|
| G1 | **BLOCKER.** `pkgs[name] = (version, src)` keys on NAME only. The lock has 346 `[[package]]` blocks but 310 distinct names — 25 names resolve at 2-4 versions at once. Last-block-wins on an ascending-sorted file means only the **highest** version of a duplicated name is ever compared, so re-pinning a lower duplicate passed as "OK" (safety property failing **open**) | Comparison rebuilt over `name -> SET of versions` |
| G2 | The same dict fails **closed** on a legitimate removal: dropping the `base64 0.23.1` block made the map read `0.23.1 -> 0.22.1` and exit 1, though the plan explicitly permits removals | Same fix: a version disappearing with none appearing is a removal, permitted. A violation requires a version to disappear **and** a different one to appear for the same name |
| G3 | A 0-byte or header-only lock exited 0 — every package read as removed, and removals are permitted — and would have been committed and force-pushed onto the release PR | Floor check: the lock must parse to ≥ 50 package blocks **and** contain all seven internal crates plus `macp-integration-tests` |
| G4 | A `[[package]]` block missing its `version` key was skipped by `if n and v:` and so read as a *removal* | Malformed input now fails loudly with the block index |
| G5 | The source-less exemption `not (osrc or nsrc)` was correct but undocumented as to *what* it covers | Comment now names `macp-integration-tests 0.0.0` explicitly and records the residual: a third-party crate `[patch]`ed to a path would silently gain the exemption |
| G6b | Push target derived from `git rev-parse --abbrev-ref HEAD`. Works for same-repo PRs; for a fork `gh pr checkout` names the branch `<owner>-<branch>` and the push would create a **new branch** instead of updating the PR | Push to `fromJSON(needs.release-plz.outputs.pr).head_branch`, with an empty-value guard |
| G7 | No `timeout-minutes`; the job inherits the 360-minute default while holding the `release-plz-<ref>` concurrency group | `timeout-minutes: 15` |
| M1 | The step only proved nothing *bad* moved; it never proved the sync **worked** | Added a `cargo metadata --locked --manifest-path integration_tests/Cargo.toml` step — `--locked` makes cargo refuse to write, so a partial or no-op repair fails |
| M4 | `git add integration_tests/Cargo.lock` would leave a modified root `Cargo.lock` dirty and silently dropped | `git status --porcelain -- Cargo.lock` asserted empty after regeneration |

The two proven round-1 false negatives, reproduced against the shipped `bb7a4bb` script:
`base64 0.22.1 -> 0.22.2` exit **0** "OK", and `thiserror` + `thiserror-impl`
`1.0.69 -> 1.0.70` exit **0** "OK". The proven false positive: removing `base64 0.23.1`
exit **1**. Also exit 0 under `bb7a4bb`: an empty lock, and a `tokio` block with its
`version =` line stripped.
