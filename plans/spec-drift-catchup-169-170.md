Verdict `drift=yes`, issue filed. That is #170, and it is a false positive twice over.

**Why the fix is not "narrow the diff scope".** Issue #169 asks for annotation-stripping on `schemas/json/policy/**`. That is right, but the obvious implementation — filter the `diff` so these files stop being compared — is wrong, and the #122 edit is the proof. The `$comment` it rewrites now states a **MUST**: RFC-MACP-0012 §4.1 (`1.6.0-draft`) gained a normative paragraph, "Vacuous participation floor (schema_version ≥ 3)", and the schema's annotation restates it. So an annotation-only schema diff can carry brand-new normative text that **no mechanical gate in this repo can see** — `check_dir` never reads this tree at all, and the parity test reads fourteen keyword pointers. Making such a diff invisible would hide the very signal that produced #169's second and larger ask. The design therefore separates **escalation** from **visibility**: no GitHub issue, but the suppressed entries and the literal annotation diff go to the step summary and the run's annotations.

**#169's substantive half.** Spec #122's normative text:

> **Vacuous participation floor (schema_version ≥ 3).** […] When that floor is effectively zero — `voting.quorum` absent, or `value: 0` under either the `count` or the `percentage` type, which are the same declaration — the flag gates nothing: `require_vote_quorum: true` is equivalent to `require_vote_quorum: false`, and a runtime MUST evaluate it as such. […] a runtime MUST NOT reject the descriptor at admission for it and MUST NOT substitute a floor the policy did not declare, though tooling MAY warn. This equivalence is scoped to `schema_version ≥ 3`.

This runtime already satisfies every clause, at both layers, and **has no test for any of it**:

- **Evaluation.** `require_vote_quorum` has exactly two decision-affecting reads in the whole workspace, both in `crates/macp-policy/src/evaluator.rs`: the quorum gate at `:353` and the legacy `schema_version <= 2` empty-tally arm at `:463`. **One claim in the briefing this plan corrects.** The `percentage` + zero-declared-participants branch was flagged as a divide-by-zero risk that is "live and reachable in production". **It is neither.** The division is already guarded — `check_quorum:574-575` returns `value <= 0.0` when `total_participants == 0` and never divides. ## Design questions answered

**1. Suppress escalation, or narrow the comparison?** Suppress escalation; keep the comparison wide. Narrowing `diff -rq`'s scope to `*.json` (mirroring `check_dir`) would make `lint_fixtures.py`-class changes *invisible*, and those changes are leading indicators even when they demand nothing: a linter that starts requiring a key is how you learn the fixture corpus is about to move. (It did not this time — all 17 policy-bearing fixtures already comply, measured — but that is a fact about this commit, not about the class.) The same argument runs harder for `schemas/json/policy/**`, where annotation text is where the spec records normative reasoning and, in #122's case, an actual MUST. So the workflow keeps seeing everything and stops *filing an issue* about the subset it can prove is mechanically inert.

**2. Is proving "mechanically inert" actually sound for a policy schema?** For the two gates, yes, and the argument is by construction rather than by inspection. `check_dir` reads `tests/conformance/*.json` and `tests/conformance/cmt-hash/*.json` against the same two canonical directories (`ci.yml:603`, `:615`, `:624-625`) — it **never opens `schemas/json/policy` at all**, so no change there can fail it. The only mechanical consumer of that tree is `enum_lists_match_the_canonical_schemas`, which reads fourteen pointers, every one of them a schema keyword (`enum`, `exclusiveMinimum`, `maximum`, `minimum`, `minProperties`, `required`, `type`, `const`). Deleting `description`, `$comment` and `title` at every depth cannot change any of them. So a diff that vanishes under that strip provably cannot move either gate. What it *can* move is a human's understanding — hence the visibility requirement in Phase 1, which is not decoration.

**3. Which direction does the suppression fail?** Closed, everywhere, and the classifier is written so that the *default* branch is "actionable". Only two shapes are suppressible, both positively matched: a non-`.json` path under `schemas/conformance/`, and a `schemas/json/policy/*.json` path that survives the strip test with an explicit zero exit. Everything else — an `Only in …` line in either direction, any `schemas/conformance/**/*.json` byte diff, a `jq` failure, a malformed file, an unparseable diff line, a stderr line captured by the `2>&1` — lands in the actionable list untouched. A `schemas/conformance/**/*.json` file must **never** be annotation-stripped: `check_dir` demands byte identity, and the fixtures' own `_comment` and `description` keys are load-bearing bytes there even though our loader drops them.

**4. Does the pin bump need vendoring, mirror edits, or new behaviour?** No, no, and no — and this is measured rather than reasoned. See the Context table: all three oracle steps are green against the new pin at `5e95c4a` with no repo change. The `lint_fixtures.py` change is not a mirrored artifact; the schema change is annotation-only. Issue #170's checklist items 1 and 2 are therefore satisfied vacuously, and item 3 ("implement any new normative behaviour") is satisfied by the pre-existing implementation that Phase 3 finally tests. Do **not** let the checklist's wording drive make-work.

**5. Why is the `make_policy()` default the single biggest hazard in Phase 3?** `make_policy` (`evaluator.rs:1102-1110`) sets `schema_version: 1` (`:1108`), and `decision_policy` in the registry tests does the same (`registry.rs:1212`). At v1 and v2 the `:463` arm gives `require_vote_quorum` a **second, independent** role that a zero floor does not disable — RFC-MACP-0012 §4.1 "Legacy empty-tally rule", retained deliberately so stored sessions replay identically (§8), and already pinned by two tests. A new "equivalence" test built on the default would therefore exercise the *legacy* regime: on an empty tally it would go red for the right-looking reason and the wrong actual one, and on a non-empty tally it would go green without ever touching the rule it claims to pin. **Every new test in Phase 3 sets `schema_version = 3` explicitly, and one test exists solely to pin the v2 divergence** so a later "simplification" that extends the equivalence to all versions goes red.

## Phases

Phases 1, 2 and 3 are **mutually independent**. They touch three disjoint file sets (`spec-drift.yml`; `ci.yml`; `macp-policy` + `docs/policy.md`), share no symbol, and each is separately verifiable. Ship them as one PR with three commits — the two issues are one story and the PR body wants to tell it once — but any one can be dropped or landed alone without touching the others.

One **ordering hazard**, not a dependency: once Phase 2 lands, `spec-drift.yml`'s `head_sha == PINNED` short-circuit (`:82-86`) fires on the next run and returns `drift=none`, so Phase 1's new classification can no longer be exercised by a scheduled run or a `workflow_dispatch`. Phase 1's acceptance is therefore written against a **local harness over the real `c137f73 → 0de1fab2` pair**, which works before and after Phase 2 and does not depend on GitHub scheduling at all.

  The classifier is a `while IFS= read -r line` over the raw report. A `case` matches only the literal shape `Files spec-pinned/… and spec-head/… differ`; every other line — `Only in …` in either direction, anything on stderr — is appended to `actionable` unexamined. For a matched line, extract the relative path as field 2 with the `spec-pinned/` prefix stripped, then **guard the extraction**: if neither `spec-pinned/$rel` nor `spec-head/$rel` is a regular file, the extraction was wrong (a path containing a space truncates at `awk $2`) and the line is actionable. That guard is what stops a hypothetical `schemas/conformance/my file.py` from being suppressed under a truncated name.

  Classification of a guarded `$rel`, first match wins, so the ordering of the two `schemas/conformance` arms is load-bearing:

  1. `schemas/conformance/*.json` — **actionable, always.** Note that shell `case` globs match `/`, so this arm also covers `cmt-hash/*.json` and anything deeper, which is the conservative reading `check_dir` deserves.
  2. `schemas/conformance/*` — suppressed, reason "not a `*.json` fixture; outside `check_dir`'s glob".
  3. `schemas/json/policy/*.json` — suppressed **iff** the strip test passes.
  4. anything else — actionable.

  The strip test is a shell function comparing `jq -S 'walk(if type == "object" then del(.["$comment"], .description, .title) else . end)'` over the two files, returning non-zero on any `jq` failure so malformed or unreadable JSON is actionable. **Single-quote that program.** Measured on this machine (shellcheck 0.11.0, and `actionlint` on a probe copy of the workflow): the single-quoted form raises **no SC2016** and actionlint exits 0 — shellcheck recognises `jq` and does not treat its program text as a shell string. The file's own header note about single-quoted backticks and SC2016 (`:76-78`) is about plain string literals reaching the *issue body*; it does not generalise to a jq argument, and an earlier draft of this plan wrongly said it did. What **is** a real trap is `set -u`: double-quoting the program makes `$comment` an unset-variable expansion and aborts the step. So: single quotes, not double, and no heredoc gymnastics needed. The other real constraint is that the step runs under GitHub's default `bash -e {0}` *on top of* the file's own `set -uo pipefail` (`:79`), so `-e` is live and every command whose non-zero status is expected needs `|| true` or an `if`, exactly as the existing `diff … || true` does.

  Verdict becomes a three-way: `drift=yes` if `actionable` is non-empty; `drift=non-actionable` if only `suppressed` is non-empty; `drift=prose-only` if both are empty. Adding a fourth verdict value rather than folding the new case into `prose-only` costs nothing and keeps the run summary honest about which of the two happened. Both the issue-filing condition (`:143`, `== 'yes'`) and the close condition (`:167`, `!= 'yes'`) keep their current tests unchanged and both do the right thing with the new value. (Checked: a step `if:` carrying no status function is implicitly `success() && …`, so a *crashed* diff step skips both — the classifier cannot fail open into an auto-close.)

## Long-term posture

**The drift watcher's scope is narrower than the spec changes that affect this repo, and Phase 2 crosses a live example.** Both `conformance-oracle` and `spec-drift.yml` watch exactly two trees. Spec #120 changed `schemas/json/macp-policy-descriptor.schema.json` — the schema for the descriptor this runtime's `RegisterPolicy` accepts — and it sits in neither. We are conformant to it by luck of proto3 semantics rather than by a gate (Phase 2's edge cases; Open question 3). The honest framing is that the pin plus the watcher make a *subset* of spec drift mechanical, and the subset boundary is invisible from inside either job. Adding `schemas/json/macp-policy-descriptor.schema.json` to `spec-drift.yml`'s tree list would be a one-word change and would have surfaced #120 as a tracked item; it is not in this plan because widening the watcher's scope without a corresponding gate in `conformance-oracle` files issues nobody can discharge mechanically, which is the noise trap the workflow's own header comment (`:16-19`) warns about. The right sequencing is: first give the descriptor schema a parity assertion, then widen the watcher. Both are follow-on work.

**Hand-written schema mirrors still catch only what someone thought to mirror.** `enum_lists_match_the_canonical_schemas` now carries fourteen assertions and has grown once per spec change (#99 added `minProperties` and the `majority` arm; #110 the quorum floor; #112 the `supermajority` `required`). Phase 1's annotation-strip is safe *because* the test reads keywords only — but the same fact means a new keyword upstream is invisible to both the parity test and, now, to the drift watcher when it lands in a commit whose other changes are annotations. That combination is not reachable today (a new keyword changes the stripped structure, so the diff is actionable), but it is worth stating plainly: the strip suppresses *escalation of a proven-inert diff*, and "inert" is defined against the gates we have, not against the spec. The structural answer remains a generated mirror or a JSON-Schema evaluator behind a dev-dependency, unchanged from the #99 plan's assessment and still not urgent.

**Workflow logic has no test harness in this repo.** Phase 1 adds real branching to a file that gates nothing, so a regression is silent by construction — the watcher would simply stop reporting. The local harness discharges that at authoring time and then evaporates. A committed harness (a small script plus two pinned revision pairs as fixtures) would make the classification a standing gate; nothing like it exists here today and adding one is a meaningful scope increase for a workflow that files issues rather than blocking merges. Open question 4.

**`schema_version` remains a semantic axis and this is its second use.** `evaluator.rs` now carries two `policy.schema_version >= 3` comparisons in spirit — one explicit at `:456`, one implicit in the fact that `:353` is the flag's *only* remaining role at v3. The #99 plan's rule of thumb was "one comparison does not justify an abstraction; three will". Phase 3's tests are the first thing that names the v3-only equivalence in code; if a third semantic version lands, the named-predicate-on-`PolicyDefinition` refactor becomes due, and the new `docs/policy.md` bullet is where the version table should live in prose until then.

## Enterprise concerns

**Upgrade blast radius: none.** No phase changes runtime behaviour, no public API moves, no environment variable is added or reinterpreted, no stored session replays differently, and no policy that registers today stops registering. `cargo semver-checks` must report **no new failure** relative to `5e95c4a` (Phase 3 criterion 9 — note the absolute "no semver update required" form is already false at HEAD, because `7c652b6` carries the two breaks `CLAUDE.md` §8a records as forcing `0.8.0`; this work simply adds none), and the conventional-commit types should reflect that — this work is `ci:`, `test:` and `docs:`, with no `!` marker anywhere. That matters concretely: `release-plz.toml` puts all seven crates in one `version_group` with `semver_check = true`, so a stray breaking marker would cut a major for a PR that adds two tests and a YAML line.

**What actually changes for a maintainer.** One thing, and it is a policy change worth stating in the PR body: the `spec-drift` label will stop appearing for a class of upstream change it used to appear for. Anyone who has learned to read that label as "the spec moved in a tree we mirror" now needs to read it as "the spec moved in a way our gates can act on". The step summary carries the rest, and `docs/testing.md` records the distinction (Phase 1 Docs). The failure mode to guard against is the opposite of the one #169 reports: not noise training people to ignore a real signal, but silence training them to assume there is none. The bounded, mandatory visibility in Phase 1 — summary, `::notice::`, the literal annotation diff, and the suppressed count echoed into any issue that *is* filed — is the whole of the mitigation, and it should not be trimmed for tidiness.

**Governance semantics under operators' feet: unchanged, and now documented.** The vacuous-floor equivalence has been this runtime's behaviour since before `schema_version: 3` existed here; Phase 3 changes nothing an operator observes. What it changes is that an operator reading `docs/policy.md` can now *learn* that `require_vote_quorum: true` over `policy.default`'s own `count: 0` gates nothing at v3 — which, given that `policy.default` ships exactly that floor (`crates/macp-policy/src/defaults.rs:13`), is a question a real deployment will ask. The three reserved `policy.std.*` profiles are unaffected: all set non-zero floors (`count: 1`, `count: 2`, `count: 1`) at `schema_version: 1`.

**Release shape.** Nothing here forces or forbids a version bump; release-plz will compute one from the commit types. Read `[workspace.package].version` in the root `Cargo.toml` rather than trusting any number written down, and re-check the semver summary per crate at ship time (`DECISIONS.md` **D7** — the tool exits 0 while printing "requires new major version", so the exit status is not the signal).

## Open questions

1. **Should the `check_quorum` table include satisfied-percentage cases?** — **Decided: yes, included** (Phase 3, test 5). The briefing flagged it as adjacent scope. It is three lines, it closes a coverage hole the audit found (no test in the repository has ever exercised a percentage quorum being met), and without it test 4 cannot be falsified. Recorded as a decision rather than left open.
2. **Should the registry emit a warning on `require_vote_quorum: true` over a zero floor at `schema_version >= 3`?** RFC-MACP-0012 §4.1 explicitly permits it ("though tooling MAY warn") and calls the combination "an authoring smell". Not done here: it is a behaviour addition to a phase that claims none, and it needs a decision about where a registration warning surfaces (`tracing::warn!` at `register` time is invisible to the caller, and `RegisterPolicyResponse` carries only `ok` and a message with no warning channel). Worth its own issue; note that the same MAY would cover the `schema_version <= 2` case §4.1's "Retaining the legacy arm" already SHOULDs a warning for, which this runtime also does not emit — two warnings, one mechanism, one issue.
3. **Is this runtime conformant to spec #120's descriptor tightening, and should a gate say so?** `schemas/json/macp-policy-descriptor.schema.json` at `0de1fab2` lists `description` in `required`. `PolicyRegistry::validate_definition` (`registry.rs:291-313`) never inspects it, so an empty-string description registers. The analysis says we are conformant — proto3 makes the field always present, the schema constrains presence rather than emptiness, and the RFC's `1.5.0-draft` changelog says "Presence only: no `minLength` is imposed" — but nothing in this repo asserts that, and the file is outside both gates' scope (Long-term posture). Two sub-questions: should the descriptor schema join `spec-drift.yml`'s tree list, and should it get a parity assertion first?
4. **Should the Phase 1 classifier get a committed test harness?** The classification is real logic in a workflow that gates nothing, so a regression is silent. A committed harness with two pinned spec-revision pairs would make it a standing gate. Against: no precedent in this repo, and shell-testing a workflow step outside Actions means either duplicating the script or extracting it to a checked-in file the workflow sources — the second is the cleaner shape and the larger change. Left open deliberately; Phase 1's acceptance discharges the risk at authoring time only.
5. **Closing on `non-actionable` is a policy decision, and nothing then tracks pin age.** Phase 1 leans on the existing `!= 'yes'` close step (`spec-drift.yml:167`) doing the right thing with the new verdict, and for the false-positive it removes, it does. But the consequence is that once Phase 2 lands, an inert drift leaves **no tracked artifact at all** saying the pin is behind — the watcher goes green and the pin can age indefinitely behind it, which is the rot the pin-plus-watcher design exists to prevent. Criterion 7's close-comment wording mitigates (it says the pin remains behind) but nothing durable tracks it. Three options, none taken here: file nothing but leave an *existing* issue open with a comment on `non-actionable`; add a pin-age threshold that escalates regardless of classification; or accept it and record the reasoning in `DECISIONS.md`. The third is the cheapest and probably right, but it is a decision rather than an implementation detail, so it should not be made silently inside a workflow edit.
6. **`voting.quorum.value` with no `type` key silently defaults to `count`, not `percentage`** (`crates/macp-core/src/policy/rules.rs:52-53`, `:67`). Not a #122 concern — the *value* default is `0.0` (`:55`), which **is** the zero floor, so no floor is substituted and the MUST is satisfied — but the *type* default is a silent substitution of one of two semantics, and `{"value": 50}` means "50 voters" where an author may have meant "50 percent". The canonical schema carries `"default": "count"` so the behaviour is conformant; the question is whether a policy supplying `value` without `type` should be refused at admission on the same fail-at-authoring-time argument that carried spec #149. Documentation-only observation, filed here rather than fixed; Phase 3 pins the current behaviour in test 1's fourth spelling either way.
